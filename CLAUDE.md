# CLAUDE.md

Upstream Kuma (formerly BlueHole, and before that Waterfall Alert) is a Home Assistant add-on for hierarchical uptime monitoring (Uptime Kuma-style, but monitors form a DAG and a failure sends one root-cause alert listing everything downstream).

**Names:** user-facing text says Upstream Kuma; identifiers are `upstream_kuma` (add-on slug and directory), `upstream-kuma` (repo `big-barlowe/upstream-kuma`, image `ghcr.io/big-barlowe/upstream-kuma`, `package.json` name, the database file `upstream-kuma.db`) and the `upstream-kuma:` storage-key prefix. Everything was renamed in 0.16.0, before any real release. From now on the slug and the image name are fixed: changing the slug makes Home Assistant treat it as a new add-on (no data), and the image name is in people's compose files. server.js still renames an old `waterfall.db` in the data folder on startup.

## Commands

Run everything from `upstream_kuma/app`. Node may not be installed locally; Docker always works:

```sh
# tests
docker run --rm -v "$PWD":/app -w /app node:22-alpine sh -c 'npm install --no-audit --no-fund && npm test'

# run the real add-on image locally
docker build -t upstream-kuma:dev ..   # from upstream_kuma/app, context = upstream_kuma/
docker run -d --name uk-dev -p 8099:8099 -e DATA_DIR=/tmp/data upstream-kuma:dev
docker cp public/. uk-dev:/app/public/  # hot-swap frontend without losing data (static files are read per request)
```

With local Node ≥ 22.13: `npm install && npm start` / `npm test`.

To look at the UI: headless Chrome screenshots work (`--headless=new --virtual-time-budget=4000 --screenshot=…`). Its viewport never goes below 500px wide, so a `--window-size=400,…` shot is cropped, not reflowed.

## Hierarchy semantics (engine.js)

- Statuses: `DOWN=0, UP=1, PENDING=2, BLOCKED=4` (`status.js`). BLOCKED means "not checked because upstream is down".
- **Gate**: `gateState(id)` looks at the parents. `parentMode: 'all'` (default) is blocked if any parent is down; `'any'` is blocked only if all parents are down. Groups and paused monitors are *pass-through*: they inherit their own gate and never block on their own.
- **Check flow** (`#doCheck`): gate closed → record BLOCKED, no network call. Otherwise run the checker → retries (PENDING) → on confirmed failure, `#verifyUpstream` force-checks the parents first. If a parent is down the monitor becomes BLOCKED, if a parent is still retrying it stays PENDING, and only otherwise does it go DOWN, block its descendants, and send one alert listing them.
- **Recovery**: an UP after DOWN/BLOCKED triggers `#cascade`, which immediately checks the BLOCKED children; they cascade further, one level at a time. The `up` alert goes out on DOWN → UP, and also whenever the monitor's last down alert hasn't been answered (`store.openEpisode()` reads the alerts log: DOWN → BLOCKED → UP, restarts); its duration counts from the first down alert. `#channelsFor` sends `up`/`resolved` to the rules' channels plus every channel the alerts it answers went to.
- Alerts are raised for the **root-cause monitor** only; notification rules pick the channels (see below). Every alert is logged in the `alerts` table, sent or not: `#dispatch` logs it first with `delivered` entries `{id, name, pending: true}`, then `setAlertDelivered()` once `notify` (= `deliver()`) returns. `deliver()` retries each channel after `RETRY_DELAYS` (5s, 30s, 2min) unless the error is `permanent` (a 4xx other than 408/429, a missing setting); `post()` always reads the reply and turns timeouts and `fetch failed` into readable errors. Send test passes `retries: []`.
- `check(id, {urgent, fresh})` dedupes concurrent checks via `rt.inflight`. The checker runs in a slot (`#slot()`, pools `CONCURRENCY = {snmp: 4, other: 16}`; push takes none), so a cascade or the startup sweep queues instead of starting hundreds of pings and SNMP walks at once (that starved small hosts: healthy SNMP devices timed out and alerts sent meanwhile hung). `urgent` (refresh, i.e. edits and Check now, and `#verifyUpstream`) goes ahead of routine checks and hurries one already waiting; `fresh` (refresh) chains another check when one is already running with the old config. The gate is tested again once a slot is free. `#scheduleNext` adds ±5% jitter (`jitter` option) so monitors don't all fire in the same second. Fire-and-forget work goes through `#track()` so tests can `await engine.idle()`.
- The engine takes injectable `checkers`, `notify`, `now`, `schedule`, `cancel`, `concurrency` and `jitter`, so tests use fake checkers, a fake clock and no timers.
- After any config change the API calls `engine.reload(changedIds)`, which rebuilds the graph and re-evaluates those monitors.
- **node:sqlite is synchronous**, so a slow query stops everything (requests, check timers, SNMP replies, alert sends): the heartbeats table holds every monitor's history (90 days by default; 407 monitors × 2 weeks is 8M rows). Never aggregate over all monitors' heartbeats on a request or timer; query one monitor through `heartbeats_monitor_time`. The 24h `uptime24`/`avgPing24` in `/api/state` come from per-hour counts in memory (`rt.hours`, loaded once by `#loadHours()` from `uptimeHours()`, counted in `#record`); `api/monitors/:id/uptime` is `store.monitorUptime()` (one pass over that monitor's 30 days); `#prune` deletes in `PRUNE_BATCH`es with a `setImmediate` between them. An aggregate over everything took 13s at one core and froze the server on every monitor page view.

Edges are stored once (`monitor_edges(parent_id, child_id)`). "Dependents" are just the reverse view, which is why adding a parent automatically lists the monitor as that parent's dependent. Cycles are rejected in `api.js` (`applyEdges` → `Graph.hasCycle`), and the form hides options that would create one.

Moving goes through `moveMonitors()` in api.js (`POST api/monitors/move {moves: [{id, fromParentId}], toParentId, link}`; the single `api/monitors/:id/move` route uses it too). A missing `fromParentId` (picked in the Falls) replaces all parents; a monitor whose from-parent is also being moved is left alone ("along"), so subtrees keep their shape. All in one `store.tx`.

## Collected data (SNMP)

- A checker is called as `fn(monitor, { previous })` and may return `data` with its result. The engine stores it (`store.setMonitorData`, table `monitor_data`, one JSON row per monitor) after any check that returned it, and passes it back as `previous` next time; a failed check leaves the last snapshot. `PUT api/monitors/:id` clears it when the type or config changes.
- **Display settings** are config keys `oids`, `hide` (e.g. `fact:contact`, `if:<name>`, `res:<name>`, `section:<name>`) and `card` (≤ `CARD_MAX` keys: `name`, `uptime`, `ifs`, `cpu`, `memory`, `disk:<name>`, `if:<name>`, `value:<oid>`). They are `DISPLAY_KEYS`: changing them never clears the snapshot. `PUT api/monitors/:id/snmp-display` saves them and reloads the monitor, because the card text is the check's `msg` (`cardText()` in checkers/snmp.js), which `subline()` in flow.js shows for SNMP cards. `GET api/monitors/:id/snmp/walk?start=` returns a page of a live walk of the whole tree for the browser (`#/monitor/:id/snmp`).
- `GET api/monitors/:id/data` → `{ at, data, display }`. It is not in `/api/state` (too big); the frontend fetches it through `snmpSnapshot(id, lastCheck, onLoad)` in `public/js/snmp.js`, which refetches only when the monitor's `lastCheck` changes.
- The SNMP checker's uptime test is the system-group GET (half the timeout per try, one retry). Everything else (IF-MIB ifTable/ifXTable columns, HOST-RESOURCES CPU and storage, UCD ssCpuIdle as a CPU fallback, the `oids` config) is best effort within a deadline; failures go into `data.notes`. Rates come from `previous` (32-bit wrap handled, reboots and 64-bit resets skipped).

## MIBs (mib.js)

- `parseMib(text)` → modules `{ name, imports, defs, types }`; it is a lenient SMIv1/v2 subset (comments run to end of line, MACRO bodies skipped, a SYNTAX is parsed as a type so a TEXTUAL-CONVENTION ends where its SYNTAX does). `MibLibrary.compile()` resolves OIDs across modules through imports, falling back to any module that defines the name and then to well-known roots; uploaded modules outrank bundled ones, RFC1213-MIB ranks lowest.
- `label(oid)` names an instance only from an object with a SYNTAX (or an exact match), so vendor OIDs under nothing but `enterprises` stay unnamed; `near(oid)` gives the subtree to look up instead. `formatValue(entry, vb)` → `{ text, raw? }` (enums, BITS, integer `d-N` hints, RFC 2579 octet hints, DateAndTime, units, OID values by name).
- The current library is a module singleton (`mibLibrary()` / `setMibLibrary()`). `createApi()` builds it from the bundled files plus the `mibs` table (one row per module; a file with several modules is split with `splitModules()`), and the MIB routes (`GET/POST api/mibs`, `DELETE api/mibs/:name`) rebuild it and `engine.reload()` the SNMP monitors so card text follows. `POST api/mibs` has the 32 MB body limit.
- The walk route (`snmpBrowse`) sends per entry `name`, `text`, `raw`, `obj` (key into the page's `objects`: module, type, units, access, desc) or `near`; custom values in snapshots carry `text`. Lookup links (oidref.com, mibs.observium.org) are plain links the user clicks; the server never contacts them. MIBs are not part of the CSV.

## Icons

- A monitor's `icon` column holds a spec: `''` automatic (favicon for HTTP, the status-reply icon for Minecraft, folder for groups), `none`, `builtin:<name>` (or `builtin:<name>:#rrggbb` for a coloured glyph: the descriptor gets `color`, which `iconEl()`/`iconSvg()` set as the CSS `color` the glyphs stroke with; the picker's colour row is in `iconChooser()`), `emoji:<text>`, `url:<url>`, `upload`. Parsing and validation are in `src/icons.js`.
- `IconCache.sync(monitors, forceIds)` runs after every monitor create/update/delete and every 6h. It drops images nothing wants and fetches missing or stale ones in the background, then calls `engine.touch()` so the UI polls them in.
- `/api/state` replaces each monitor's spec with a render descriptor from `icons.describe()`: `{kind:'image', src}`, `{kind:'builtin', name}`, `{kind:'emoji', value}` or `null`. `GET api/monitors/:id` still returns the raw spec, which is what the form edits.
- Images are served from `api/monitors/:id/icon` with a sandboxing CSP, because SVGs come from arbitrary sites and the add-on shares Home Assistant's origin. Keep those headers. Types are sniffed from bytes (`sniffImage`), never from Content-Type.
- Built-in glyph keys are stored in the database, so never rename one in `public/js/icons.js`. Adding one is fine.
- **Icon size**: `monitors.icon_size` (percent, 50–200, `ICON_SIZE` in validate.js; CSV `icon_size`) scales image icons only. `describe()` adds `size` (a factor, absent at 100) to image descriptors, including a tag's image shown on the monitor; `iconEl()` scales the `<img>` (its `.mon-icon` clips), `iconSvg(icon, cx, cy, size, clip)` scales the `<image>` and, above 1, clips it with the shared `badge-clip`/`group-clip` clipPaths in the Falls' defs (userSpaceOnUse, so one each serves every node). `iconChooser({ size })` shows the slider and the circle/badge preview for image modes.
- **Tag icons**: `tags.icon` holds the same kind of spec (`''` = no default, never `none`); an uploaded one lives in `tags.icon_data` and is served from `api/tags/:id/icon`. A monitor whose own spec is `''` takes the first tag (in tag order) with an icon, ahead of favicons: `tagIconSpecs()` builds that map in `IconCache.sync()`, and `#spec(m)` is what `wanted()`/`describe()` use. A tag image URL is cached per monitor like any URL; a tag upload becomes the internal spec `tag:<id>@<version>`. So **anything that changes tag icons or which monitors carry a tag must call `iconsChanged()`** in api.js. The form's icon picker is `iconChooser()` in forms.js, shared with the tag icon dialog. Tag icons are not part of the CSV.

## Notification rules

**Wording:** the UI calls the configured objects (`problems` table, `api/problems`, `PROBLEM_KINDS`) **problem definitions**; a **problem** is an open one on a monitor (`problem_state` with `state = 'open'`, `engine.openProblems()`). Code and routes keep the short name; user-facing text must not call a definition a "problem".

- `notification_rules(channel_ids, problem_ids, tag_ids, tag_match, tag_expr, downstream, min_severity)` (JSON id lists) and `problems(kind, name, severity, config)`. A rule reads "Alert <channels> when <problems> for <tags>": empty `problem_ids` = any problem (of at least `min_severity` if set), no tags = all monitors, `tag_expr` (filter.js syntax) replaces the pills when set. `downstream`: also fires when the monitor at fault is untagged but one of the monitors its alert lists (affected / resuming) matches.
- `matchRules()` in `public/js/rules.js` is the only matching code; `#channelsFor()` in engine.js and the monitor form both call it. The engine imports it (and api.js imports filter.js) from `../public/js/`, which is why those two files must stay import-free apart from each other.
- Problem kinds: `down` (built in, id 1, always `severe`) covers the down alert, reminders and the `up` alert; `config.recovery: false` stops resolved alerts. A new kind needs an entry in `PROBLEM_KINDS` (problems.js) and a place in the engine that dispatches it.
- Severities are `SEVERITIES` in rules.js (`info` < `warning` < `severe`). `/api/state` carries `problems` (id, kind, name, severity) and `open` (`engine.openProblems()`: DOWN monitors as the down problem, plus open value problems, `stale` when the monitor isn't up). app.js sets `m.sev` (`monitorSeverity()`: highest open value problem, only while up) and `m.issues`; flow.js adds `sev-warning`/`sev-severe` to the node in `#paint`, and the list shows `sevMark()`. `notifier.js` `level(a)` maps kind + severity to loudness.
- Safety rules: a rule never silently widens. Deleted tag ids stay in `tag_ids` (only live ones count; none live = matches nothing and the page shows it in red), a broken expression matches nothing, and renaming a tag rewrites expressions (`renameInExpr()` in the tag PUT route). Unknown channel and problem ids are dropped on save.
- Rules only route alerts, so changing them needs no `engine.reload()`. They and channels are not in the CSV; an old file's `notifications` column is ignored with a warning.
- **Value problems** (kind `value`, `src/problems.js`): `config = { tagIds, tagMatch, tagExpr, readings, checks, recovery, downstream }`, scope tested with `ruleTagTest()` like a rule (none = every SNMP monitor). A reading is `{ source: 'oid'|'cpu'|'memory'|'disk', oid?, op: 'in'|'not-in'|'<'|'<='|'>'|'>=', values?|value, label?, names?, where? }`; `where: { sysObjectId?, monitorIds? }` keeps it to one model (exact `data.system.objectId`) or to those monitors (`readingApplies()`, so `evaluate(problem, result, monitor)` needs the monitor). A monitor uses the **first applicable reading it answers**, none answered = `unknown` ("can't be read"). The engine's `#watching(m)` picks the problems for an SNMP monitor, `probeOids()` goes to the checker as `fn(m, { previous, probe })`, which GETs them right after the system group and returns `result.probe` (`undefined` if that GET failed: then the engine skips OID problems rather than calling them unknown). `#evaluateProblems()` runs after a successful check: `checks` hits in a row open it (alert kind `problem`), a non-hit closes it (kind `resolved`), `unknown` leaves an open one open, a monitor no longer in scope is forgotten silently. State is `engine.pstate` (memory) mirrored in `problem_state(problem_id, monitor_id, state, since, value)`, so restarts don't re-alert. `downstream: true` lists every active descendant in the alert without blocking anything. Routes: `GET/POST api/problems` (with `coverage`), `PUT/DELETE api/problems/:id` (delete drops the id from rules and deletes rules left with no problem, so none widens to "any"); create/update `engine.reload()` the watched monitors. `GET api/mibs/object?oid=` names an OID and its enums for the form. `GET api/monitors/:id/problems` lists the value problems watching one monitor with `state` (`open`/`ok`/`unknown`/`waiting`/`notSnmp`) and `reading` (index of the reading it answered, kept in `pstate` memory only, so null until the first check after a restart); the monitor page's **Monitored data** section (`monitoredData()` in problems.js) shows it. **Picking a value**: the All data browser (`renderSnmpBrowser(main, m, { pick, navigate })`, route `#/monitor/:id/snmp?pick=<definition id>`) has a **+ Problem** button per row that opens `pickValueDialog()` (problems.js): test (`readingTest()`, shared with the definition form), label, `where`, and a target definition (PUT with the reading appended) or a new one (draft in sessionStorage `upstream-kuma:newDefinition`, taken by `takeDraftDefinition()` when Settings → Notifications renders and passed to `renderProblemsSection({ draft })`). "Can't be read" monitors link to it with **Pick a value**, refetched when the monitor's `lastCheck`, tags or the problem list change. Tag renames rewrite problem expressions too.
- Migration v7 is a function (a `MIGRATIONS` entry may be one): it turned the old `monitor_notifications` into rules (a channel on every monitor → an all-monitors rule; otherwise an `Alerts: <channels>` tag with a non-downstream rule) and dropped that table and `notifications.is_default`.

## Tags

- `tags(id, name, color, position)` (names unique, case-insensitive) and `monitor_tags`. `position` (migration v9 seeded it in name order; new tags go last) is the order everywhere: `listTags()` and `monitorTagMap()` sort by it, so a monitor's tag ids, its pills and its tag icon follow it. `POST api/tags/order {ids}` (Settings → Tags → **Edit order**, `renderTagOrder()` in app.js: drag moves the row element itself, the list is redrawn on dragend) sets it. Tags have nothing to do with checking; they are display and filtering only, so tag changes call `engine.touch()`, not `reload()`.
- `/api/state` carries `tags` (all of them) and each monitor's `tags` (ids). `POST api/tags/:id/apply {monitorIds, downstream, remove}` is the bulk path; monitor POST/PUT take `tagIds` and `tagsDownstream` (adds only the *newly added* tags to every descendant).
- Tag filter (`ui.tagFilter` and `ui.tagMatch` = `any`|`all`, or instead an expression in `ui.tagExpr`, all in localStorage; setting one clears the other): `filterView()` in app.js returns `match` (monitors with any/all of the selected tags) and `show` (match + all ancestors). Ancestors that don't match get `.context` and are drawn faded, in both the tree and the Falls. A filter never drops the Falls focus: if it hides the focused monitor, `renderDashboard` keeps it and its ancestors (as context) until the trace ends.
- The list's branch lines (`.branch.flow/dry/still::before/::after` in style.css) mimic the Falls' streams: a bed with water dashes and a foam layer as SVG data-URI tiles animated by `background-position`, same sizes and speeds as the Falls' bed, water and foam. The uptime % is in the row meta's tooltip, to keep rows narrow. `renderTree()` rebuilds the rows only when `listKey()` changes (monitors, names, targets, types, parents, icons, tags, severity marks, filter, search, valve, Edit mode, collapsed branches); otherwise `refreshRows()` updates in place just the rows whose `rowState()` (status, last beat, uptime, highlight) changed, and the branches whose stream class changed: rebuilding thousands of rows on each poll froze the page every few seconds. `fitBeats()` (after a rebuild, and from a ResizeObserver on `#tree`) sets `#tree[data-beats]` to the first of full (10 beats + `.pct`)/7/4/dot that fits the widest row; CSS hides the oldest beats or swaps the bar for `.meta-dot`. A row's link is `#/?focus=<id>&info=<id>` (on a monitor's page or its All data, `#/monitor/<id>`): on the dashboard its click calls `setFocus(id, id)` instead of routing (so the Falls animates), and `setFocus()` re-renders the tree so `.row.active` follows `ui.info`. The valve (`#flow-toggle`, `ui.flatList` in localStorage) renders the list flat and alphabetical like search results. Rows only drag in Edit mode: `ondragstart` cancels any drag outside it (icons and selected text start native drags that bubble to the row), and `ondragover`/`ondrop` check `ui.editMode` too.
- Tag colours are set per element with the `--tag` custom property and mixed with `color-mix()` in CSS. `h()` routes `--*` style keys through `style.setProperty`.

## CSV import & export (transfer.js)

- `CSV_COLUMNS` drives the export, the import, the template, and the column reference on the Settings page (`GET api/csv/columns`). Adding a monitor type or config field means adding its column there **and** to `docs/csv.md`.
- Export and import must stay symmetric: export → import into an empty store must reproduce the monitors (the round-trip test checks this). References use `key` (blank = name); exports fill `key` in only for shared names or names containing `|`.
- `importCsv` runs everything inside `store.tx` and throws a private `Rollback` on any error or for `dryRun`, so the preview is exactly what an import would do. Icon uploads are returned (`uploads`) and saved by the route only after commit, because `IconCache` keeps in-memory metadata.
- Missing column = keep (update) / default (new). Present but blank = default. Except: `parents`/`tags` blank = none.
- `POST /api/csv/import` gets a 32 MB body limit (in server.js), since uploaded icons travel as data URLs.

## Falls diagram (flow.js)

- Two layouts, `treeLayout` and `ringLayout`, built on the same `structure()` (levels, primary parents, leaf slots). Both take `scaleOf(id)` (tracing: downstream monitors shrink by `SHRINK.step` per hop, down to `SHRINK.min`; the focus may also be `SOURCE` (`'source'`, exported by flow.js, `?focus=source` in the hash), which keeps every monitor and sizes it by its distance from the source via `fromSource()`. Clicking the hole (`.source`) selects it, and `this.sourceAt` stands in for the focused box when leaving that trace) and return per-card boxes `{x, y, w, h, s}` in `pos`, plus `{source, width, height, stream(from, to, seed)}`, plus `centre` for rings. A node draws at full size inside an outer `g` with `scale(s)`, so the FLIP deltas in `#animate` are divided by `k * s` and animate the size ratio too. Rings centre on the first node that branches (the chain above it is a vertical trunk), give leaves stacked staggered rows within their parent's wedge, map slots to angles (a downward fan until there are enough to fill a circle) and place nodes level by level, each just beyond its parent and pushed out along its ray until it clears everything placed (no global ring radii); `river()` draws streams in polar space with a meander, trimmed at the card edges. `setLayout()` / the corner toggle switch it, app.js keeps it in `ui.fallsLayout` (localStorage, default `rings`), and the mode is part of both the topology key and the fit key.
- `render(monitors, focusId, {selected, selectMode})`: with a focus, only `lineage()` (ancestors + descendants) is laid out. The structure is rebuilt only when the topology key changes (ids, names, edges, icons, tags, focus); `#paint` updates status, selection and `.context` classes in place so animations don't restart.
- **Groups are round and icon-only**: `dims(m, nodeH)` gives a group a `GROUP.d` circle (pool and sel-ring are rects with `rx = d/2`; `.pool-image` gives an image a light disc) with the icon centred at `GROUP.image`/`GROUP.glyph`, and no name, subline, tags or ⑂ on the node. The name is a `.group-label` pill in `g.group-labels`, a layer above all nodes (so neighbours can't cover it), placed under the circle and shown by pointerenter/focus on the node (`.show`) or for the traced group (`.pinned`). Boxes carry `round`, which `within()` (stream trimming in `river()`) and the canvas pulse use; ripples take each node's `badge` (a group's is its whole circle). The tree's rows are as tall as their tallest node (`rowH`), with the usual gap between them; rings size each node from `dims`, and the trunk stacks by height.
- Monitors passed in carry `tagList` (`[{name, color}]`) and `context`. When any shown node has tags, every node grows to `TAGGED_H` for a row of pills (widths measured on a canvas; overflow becomes `+N`).
- It is a map. `.flow-map` (the container) holds, bottom to top: the source's rim (`.flow-hole`), the streams' SVG (`.flow-streams`: beds, dry/still water), the water canvas (`.flow-water`), the cards' SVG (`.flow-svg`: `g.viewport` with the nodes, the source's hit circle and the marquee), the marks canvas (`.flow-marks`: ripples, pulses), the source's water (`.flow-hole.over`), then the controls. The four SVGs are drawn at the diagram's own size (width/height = the layout's) and moved together by a CSS transform on each (`#show`, from `this.shown`), with `will-change: transform`, so a pan only slides composited pixels. A windowed Chrome keeps such a layer at the scale it was first rastered at, so zooming in made the cards pixelated until something rebuilt them: `#sharpenLater()` (from `#show`) waits until a zoom-in settles 250ms past the layers' raster scale (`rasterK`, reset on every build; ×1.1) and drops `will-change` for two frames (`#sharpen`), which re-rasters them once. Zooming out below ×0.6 re-rasters immediately, even mid-pinch: the layer comes into view at its old, finer scale, and on an iPhone that ran out of memory ("A problem repeatedly occurred"). That wasn't enough: Safari apparently rasters a layer at the screen's resolution whatever its CSS scale, and dropping `will-change` doesn't help either (the cards SVG sits above the WebGL canvas, so it's composited for overlap anyway). So on touch devices (`COARSE`, `pointer: coarse`) below `LOD.layer` (0.5) zoom, `#show` sizes the streams and cards SVGs to `size × k` (both have `viewBox="0 0 W H"`, so the diagram scales into them) and only translates them: their layers stay about the screen's size at any zoom, pans still just move them, and each zoom step redraws them. Desktop scales full-size layers at every zoom. For the same reason the source's layers (`.flow-hole`) are 200×200 around it (`holeOrigin`, with a viewBox, offset in `#show`), not diagram-sized. Headless Chrome and CDP's `Page.captureScreenshot` re-raster by themselves and hide the problem: check it in a real window with macOS `screencapture`. The canvases are screen-sized and drawn with the same transform. The view is `view = {k, x, y, h, key, auto}`. app.js owns that object (`ui.flowView`) so zoom/position survive navigation. While `auto`, `#fit()` sizes the box and fits the diagram; it re-fits whenever `key` (focus + shown ids) changes, except when leaving a trace: then the previously focused node (`view.focus`) keeps its screen position and zoom. Pan/zoom set `auto = false`. Pointer coordinates go through `#point()` (manual inverse of the view), and the FLIP deltas are divided by `k`.
- Gestures (`#down/#move/#up`): one pointer pans, or with shift/ctrl/⌘/alt or in select mode draws a marquee (alt removes) → `onMarquee(ids)`; two pointers pinch. Wheel zooms only with ctrl/⌘ (trackpad pinch sends ctrlKey), otherwise the page scrolls and a hint shows. All pointer, click, wheel and focus listeners are on `.flow-map` (set once in the constructor; the SVGs move, the map doesn't), skipping its controls; `touch-action: none` and the grab/grabbing/crosshair cursors (`.panning`, `.selecting`) are on the map; `#origin()` is the map's inner corner for screen maths. A drag that started on a node still pans; the click that ends any drag is swallowed via `#swallowClick()`, which `#down` resets.
- Selection (`ui.selected`) is owned by app.js and shared with the sidebar tree (shift/ctrl/⌘-click rows). `ui.selFrom` remembers the parent of the tree row a monitor was picked under, for moves. `pruneSelection()` drops monitors that are gone or filtered out.
- The selection bar sits *below* the diagram and is sticky, so showing it never moves the nodes (it used to be above, and the jump made box-selecting a second time miss).
- On a rebuild, surviving nodes FLIP from their old screen position. They are positioned via the outer `g`'s `transform` attribute and animated via CSS transforms on the inner `.node-inner`, because a CSS transform on the outer one would override the attribute.
- Focus state lives in `ui.focus`/`ui.info` in app.js and is mirrored into the hash with `history.replaceState`. A real hash change would re-route and rebuild the diagram without the animation.
- **The source** is `sourceHole()`: node.svg's rim, water and core at `HOLE.scale`, centred on `HOLE.c`, drawn in two small SVGs of their own (`.flow-hole`, under and over the diagram, moved with the same transform in `#apply`); `hit`, a transparent circle in the diagram, takes its clicks, keyboard focus and hover (classes `hover`/`kbd` on the layers). The rim and water warble through SMIL `<animate attributeName="d">` frames from `warbleFrames()` (every point pushed in/out by two waves around the centre; CSS can't animate `d` in every browser). `#cull` pauses its SMIL when the source is off screen; it's left out under `prefers-reduced-motion`.
- **The canvases.** Nothing in the SVGs animates: anything that did made the browser repaint all of them every frame. What moves is drawn by `#drawWater` in one rAF loop per FlowView (`#startWater`; it stops when the map is detached, skips drawing while the map is out of the window, and runs glides via `#glideStep` so everything moves in step), with the sizes and speeds the old CSS had. **Water and foam** are WebGL2 (`WaterGL`): every flowing stream is a triangle strip from `pathPoints(d)` (rings paths are polylines, tree paths one cubic) whose vertices carry the distance along the stream (`a_s`) and the side; `WATER_FS` draws a round-ended dash wherever `s + offset` falls in the pattern, so one draw call per pass flows every stream. Geometry is uploaded only when the set of flowing streams changes (`streams()`, keyed; `#build` resets the key) and covers off-screen streams too (they cost nothing). Without WebGL2 (or if a shader fails) it falls back to dashed `stroke()`s on a 2D canvas, which are exact but slow with thousands of streams: re-dashing every curve every frame saturated the GPU process at 2,000 monitors. A lost context is set up again on `webglcontextrestored`. **Ripples and pulses** (`PULSE`) are on the 2D marks canvas, from the cards in view (`#collectWater`), cleared once when there are none. The water canvas sits under the cards, so faded (context) cards show it through. Anything that changes what's drawn calls `#waterChanged()` (sets `dirty`; under `prefers-reduced-motion` it draws one still frame instead of looping). Canvas sizes come from the ResizeObserver (`mapSize`): reading `clientWidth` in rAF forced a layout of the whole page after every poll. The water flows at every zoom; `lod-far` (below `LOD.details`) only leaves out sublines, tags, foam and ripples.
- **Performance** (stress-tested up to 4,130 monitors; check changes with a CDP benchmark driving real wheel/drag input and reading rAF frame times, long tasks and `Performance.getMetrics`, with Profiler samples and traces to find the cause): cost follows what the browser has to repaint and rasterize, not how many things move, so one shared animation in the SVG wouldn't have helped. Hence the canvases and moving the SVGs as layers, and: culled streams are `display: none` and culled cards keep only their `.pool` (so they stay focusable for Tab + `#reveal`), with a 240px margin so fast pans don't show the edge (`#paint` must keep `.offscreen`); no `:has()` selectors on the map (they re-checked it every frame); the zoom label is only rewritten when it changes (a rewrite per move cost a layout); off-screen nodes have no position, so `#build`'s FLIP `before` skips them; streams have no filter (the wide `.bed` stroke is the glow; `#glow-box` is only for single elements). What's left at thousands of monitors: any DOM animation elsewhere (list branches, status dots, the header mark, the source's warble) makes Chrome repaint and re-layerize the page each frame, a cost that grows with the page's size; they'd have to become compositor-only or canvas to remove it.

## Accounts (auth.js, oidc.js)

- `users(username, name, email, role, password, oidc_sub, oidc_name, scope, active, …)` and `sessions(token = SHA-256 of the cookie, user_id, expires_at)` (migration v11; `oidc_name` v12). Roles: `admin` and `viewer`. Passwords are scrypt (`scrypt$N$r$p$salt$hash`); sessions last 30 days, renewed while used; cookie `uk_session` (HttpOnly, SameSite=Lax, Secure over HTTPS/`X-Forwarded-Proto`).
- `Auth.identify(req)` → `{ user, via, tokenHash? }` or null: `via` is `ingress` (the Supervisor's IP under HA: a stand-in admin with id 0, named from `X-Remote-User-*`), `open` (`AUTH=off`, or `mode: 'off'` in tests: everyone is an admin) or `session`. `createApi()` requires `auth`; tests pass `new Auth({ store, mode: 'off' })`.
- **Routes have an access level**: `route(method, pattern, handler, access)`, default `'admin'`; `'view'` lets viewers in (handlers filter with `view()`, which is null for admins); `'public'` needs nothing (push, `api/info` for the healthcheck, `api/auth/*`). Anything not marked is admin-only, so a new route is safe by default. Handlers get `{ params, query, body, req, who, view }`.
- **A viewer's scope** (`{ all, tagIds, tagMatch, tagExpr }`) is tested with `scopeTest()` in rules.js (shared with users.js): unlike a rule, empty = nothing, deleted tags or a broken expression = nothing. `scopeView()` gives `match`, `visible` (match + all ancestors), `tagIds` (every tag on a visible monitor, upstream ones included: the only tags a viewer sees, filters by or loads icons of). `/api/state` drops what isn't visible (and trims parents/children/tags/open/problems), monitor reads 404 outside it, events and alerts are filtered, and `redactAlert()` cuts hidden monitors from an alert's lists and channel names. Tag renames rewrite scope expressions; user changes call `engine.touch()` so viewers' polls refetch.
- **The frontend**: `session.me` (util.js, from `api/me` at boot) and `session.admin`; `body.viewer` hides `.admin-only` (and SNMP row controls, pick links); viewers can't select; `SETTINGS` entries with `admin: true` are hidden, leaving Account. `api()` goes to `login.html` (keeping the hash) on a 401 with `login: true`; the server redirects `/` there when signed out. Static files are public.
- **CSRF**: every non-GET API request must be `Content-Type: application/json` (server.js; `api()` always sends it), which another site can't send without a CORS preflight. Push is exempt.
- **First run**: standalone with no users, `api/auth/setup` creates the admin (`setupOpen()`); never under HA (accounts are made through ingress). There must always be an active admin standalone (`keepAnAdmin`). Password, role or active changes end that user's other sessions. Failed sign-ins are throttled per IP.
- **SSO**: settings key `oidc` (`OIDC_DEFAULTS`; `getSettings()` only returns `DEFAULT_SETTINGS` keys, and `GET api/sso` never returns the secret). `api/auth/oidc/start` stores `{ state, nonce, verifier }` in memory and the state in cookie `uk_oidc`; the callback checks both, exchanges the code (client_secret_basic, else post), verifies the ID token (signature, iss, aud/azp, exp, nonce), merges userinfo, then `ssoUser()`: linked `oidc_sub` (`"<issuer> <sub>"`), else a unique verified email, else `autoCreate` (empty viewer); `adminGroup` sets the role each sign-in (never demoting the last admin). Every sign-in refreshes `oidc_name` (`ssoLabel()`: email, else `preferred_username`/`upn`, else name; `publicUser().ssoName`, shown on the Users page) and is logged with how it matched (already linked / linked now by email / new account); failures are logged too. `selectAccount` adds `prompt=select_account` to the authorize URL. Redirects are relative (`../../../`), `next` must be a `#/` route. **Home-screen apps** (`STANDALONE` in login.js) can't follow the provider (iOS shows it in a browser view of its own, which may have its own cookie jar), so they get a **handoff**: `POST api/auth/oidc/handoff` → `{id, code}` plus cookie `uk_handoff=<id>.<secret>`, the app `window.open()`s `start?handoff=<id>` (kept in the oidc pending entry) and polls `POST …/handoff/claim` (also on focus/visibility; resumed from sessionStorage after a reload). The callback: same cookie jar (has `uk_handoff`) → signs that window in too and goes to `login.html?signed-in=1` ("close this window"); another jar → no session there, cookie `uk_handoff_ok` and `login.html?handoff=confirm`, where the person compares the code and continues or cancels (`…/handoff/confirm`). Never skip that confirmation: whoever holds the handoff's cookie gets the session of whoever completes it, so a link to someone else's handoff would sign them in as you. Failures and refusals are stored on the handoff for the app's claim to report. Handoffs live in memory for 10 minutes. The redirect URI is `publicUrl` + `api/auth/oidc/callback`, or from `X-Forwarded-*`/Host; under HA `publicUrl` is required.

## Conventions

- **Layout.** `.layout` is a 3-column grid: list (`--side-w`, set by the `#side-resize` handle and kept in localStorage), handle, main. `.side`/`.main` have explicit `grid-column`s so nothing reflows when one is popped out. Pop-out (`setPopout('side'|'falls')` in app.js) adds `popout-*` body classes that make the panel `position: fixed`; it needs `align-self: stretch`, because Chrome applies `.side`'s `align-self: start` to fixed boxes and would size it to its content. `FlowView.setExpanded()` makes the map fill its box instead of setting its own height. `route()` closes any pop-out. The `.falls-resize` handle between the Falls and Recent events sets `FlowView.setHeight()` (`ui.fallsHeight`, localStorage; null = automatic).
- **Two run modes.** As an HA add-on (`isAddon`: `SUPERVISOR_TOKEN` is set), ingress requests are admins and `allowed()` in server.js limits direct port access (with `allow_direct_access` it needs an account). Standalone (Docker, `compose.yaml`) every request needs an account (see Accounts), and HA features need `HA_URL`/`HA_TOKEN`. UI text about HA-specific things should check `api/info` → `addon`.
- **Settings** (`#/settings/<section>`, `SETTINGS` in app.js: general, notifications, tags, import, mibs; `renderSettings(section)` renders `section.render(box)` into `.settings-body`). On Settings pages (`body.on-settings`) the left column shows `#settings-nav` instead of the monitor list (CSS hides the rest of `.side`, except on phones, where `.side` is the Monitors sheet and the sections are `.settings-tabs` above the page). Tags and Notifications used to be top-level pages; `MOVED` in `route()` redirects their old hashes. A new kind of setting is a new `SETTINGS` entry.
- **Phones.** `PHONE` (app.js: up to 700px wide, or a landscape phone) sets `body.phone`; everything else is CSS (`body.phone …`, the last section of style.css). The header and `.side` are hidden; `#phone-stats` (counts, filled by `renderSummary()`) and `#tabbar` (index.html; wired in `initPhone()`) are fixed bars sized from the safe areas (`--ph-top`/`--ph-bottom`; `viewport-fit=cover` and `black-translucent` put the page under the status bar). On the Falls (`body.on-falls`), `.falls` is fixed between the bars and the map is expanded (`setExpanded(ui.phone || popout)`); the card head floats over it, the map controls go bottom-right without the zoom steps (pinch instead), and `.flow-info`, `#flow-filter-pop` and `.flow-select` become sheets. The Monitors tab is the existing side pop-out (`setPopout('side')`), restyled as a sheet; the middle tab is `sourceMark()` from flow.js (`.tab svg` sizes icons, so it needs its own size). The filter is the `.filter-icon` funnel in `renderFocusBar()` (phone only; the chip and "+ Filter" are desktop), opening `#flow-filter-pop` as a sheet. On phones the trace chip's `.trace-x` replaces Show all, and `tickers()` makes `.chip-ticker` scroll (the text twice, `--shift`/`--dur`) when it overflows; `renderFocusBar()` only redraws when its HTML changes, or the poll would restart it. `swipeAway(el, close)` (touch events, from the top of the sheet's scroll; the first move decides between scrolling and pulling) closes the details and filter sheets. Inputs are 16px on phones (smaller makes iOS zoom on focus), and the map and bars swallow Safari's `gesturestart`. `manifest.webmanifest` (+ icon-192/512.png from logo.svg) makes Add to Home Screen open standalone; it needs the direct port, since a standalone app has no Home Assistant session for ingress. Test with CDP's `Emulation.setDeviceMetricsOverride` (mobile), `setTouchEmulationEnabled`, `setSafeAreaInsetsOverride` and `Input.dispatchTouchEvent` for taps and pinches.
- **No build step, no framework.** Frontend is ES modules served as-is. Keep it that way.
- **All frontend URLs are relative** (`api/...`, `css/...`, hash routes). HA ingress serves the app under `/api/hassio_ingress/<token>/`, so a leading `/` breaks it.
- Live updates are **polling** (`api/state?v=<version>` every 3s; the server returns `{unchanged: true}` when nothing changed). `engine.version` must be bumped on any state change visible to the UI.
- DOM: build with `h()`/`svg()`. Use `fill(el, …)` instead of `el.replaceChildren(…)`, because it flattens arrays and drops `null`/`false` (`replaceChildren` stringifies them into "[object HTMLDivElement]" / "null").
- CSS class names are global. Generic names collide (a heartbeat pill once used `.empty`, which picked up the dashboard empty-state padding). Prefer specific names.
- The UI is dark-only, with CSS custom properties in `:root` of `public/css/style.css`. Status colors (`--up/--down/--pending/--blocked/--paused`) are reserved for status.
- Backend has one runtime dependency (`nodemailer`, lazily imported). Uses `node:sqlite` (no native modules) and `node:http`. Don't add Express.
- Prepared statements go through `Store.q(sql)` (cached). Schema changes = append a new entry to `MIGRATIONS` in `db.js`; never edit an existing one.

## Adding things

- **Monitor type**: add a checker in `src/checkers/`, register it in `checkers/index.js` (`checkers` + `MONITOR_TYPES`), add `describeTarget` in `engine.js`, then add form fields in `public/js/forms.js` (`TYPE_FIELDS`, `TYPE_HELP`) and a label in `util.js` (`TYPE_LABEL`). Add its settings to `CSV_COLUMNS` in `transfer.js` and to `docs/csv.md`.
- **Notification provider**: add an entry to `providers` in `notifier.js` with `label`, `fields` (rendered automatically by the form) and `send(cfg, alert)`. Besides `title`/`message`, an alert carries `facts` (`[{key, label, value}]` from the engine's `compose*`), `affected` (the tree, `{id, name, depth}` in order), `upstream` (names above, through first parents) and `url` (from settings `publicUrl`, else the SSO `publicUrl`, else null), for providers that lay it out themselves: Google Chat builds a `cardsV2` card (`googleChatMessage()`), falling back to plain text if Chat refuses it (not for tests).

## Releasing

Bump the version in **both** `upstream_kuma/config.yaml` and `upstream_kuma/app/package.json` (the UI reads it from package.json), and add a `CHANGELOG.md` entry. The Supervisor offers the update when `config.yaml`'s version changes. On the push to main, CI publishes `ghcr.io/big-barlowe/upstream-kuma:<version>`, `:<major.minor>` and `:latest` (only if that version has no image yet), and always `:edge`. A version bump is therefore also the Docker release.
